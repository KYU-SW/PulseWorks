# 전자의무기록시스템 인증기준 Gap 분석

**이 문서는 이 프로젝트가 전자의무기록시스템 인증기준을 충족했다는
선언이 아니다.** 인증기관(한국보건의료정보원)의 공식 인증 절차를 거치지
않았으며, 아래 분석은 공개된 인증기준 안내 자료와 현재 프로젝트 코드를
비교한 **설계 검토용 Gap 분석**일 뿐이다.

작성일: 2026-11-05

## 0. 사용한 공식 출처

**수치 불일치 주의**: khis.kr 공식 페이지는 기능성 **27개**라고 명시하지만, 2024년 2월 보도자료는 "62개→28개"(개정 후 28개)로 서술한다. 두 수치가 다르며, 이번 조사에서 그 차이의 원인(시점 차이, 집계 방식 차이 등)을 확인하지 못했다 — **정확한 최신 세부 항목 수는 emrcert.mohw.go.kr의 세부기준 원문(위 표의 두 링크, 이번 조사에서 미열람)으로 재확인이 필요하다.**

이 보도자료는 "2025년 1월부터 적용될 예정"이라고 썼으므로, 이 문서 작성 시점(2026-11)에는 이미 그 제2주기 기준이 시행 중일 가능성이 높다. 다만 이번 조사에서 "현재 실제로 시행 중인지"를 재확인하지 않았으므로, 위 수치는 **2024년 발표 당시의 예정 기준**으로 취급해야 한다.

## 1. 상태 분류 정의

- **현재 대응 기능 있음**: 해당 기능이 모델·API·화면 어느 단계에든 실제로 구현되어 있음.
- **부분 대응**: 관련 기능의 일부만 구현되어 있거나, 구현되어 있지만 공식 기준의 세부 요건과의 일치 여부를 확인하지 못함.
- **미구현**: 관련 기능이 전혀 없음.
- **확인 필요**: 공식 세부기준 원문을 열람하지 못해 현재 상태를 기준과 대조할 수 없음.
- **현재 범위 밖**: 이번 1차 확장(VitalSign 등)에도 포함되지 않은 영역.

## 2. Gap 표

| 검토 항목 | 상태 | 현재 근거(코드/기능) | 설명 |
|---|---|---|---|
| 환자정보 | 부분 대응 | `Patient` 모델, `can_access_patient`(RBAC) | 환자 등록·조회·접근제어 기본 기능은 있음. 공식 기준이 요구하는 세부 항목(예: 환자 식별 오류 방지 절차 등)과의 일치 여부는 세부기준 원문 미확인으로 판단 불가 |
| 진단 | 부분 대응 | `Diagnosis` 모델 | 진단 기록·조회는 있으나 KCD 코드체계 적용, 확정/추정 구분 등은 없음(`kr-cdi-kr-core-mapping.md` §1 참고) |
| 검사 | 부분 대응 | `LabResult` 모델, `evaluate_lab_abnormal()` | 검사결과 기록·참고범위 비교는 있으나 표준 검사 코드(LOINC) 연계는 없음 |
| 처방 | 부분 대응 | `Prescription` 모델 | 처방 기록은 있으나 국내 의약품 표준코드 연계, 구조화된 용량 정보는 없음 |
| 알레르기 | 부분 대응 | `Allergy` 모델, `check_allergy_conflict()`(처방-알레르기 충돌 경고) | 보도자료가 언급한 "약물-알레르기 경고 기능의 필수화" 방향과 개념적으로 유사한 기능이 이미 존재하나, 이것이 공식 기준의 해당 항목과 정확히 같은 요건인지는 세부기준 원문 미확인으로 판단 불가 |
| 활력징후 | 미구현 | 없음 | `VitalSign` 모델 자체가 없음(`kr-cdi-kr-core-mapping.md` §2 참고) |
| 수술·처치 | 미구현 | 없음 | `Procedure` 모델 자체가 없음 |
| 사용자 계정·권한 | 부분 대응 | `User`/`Role`/`PatientAssignment`, JWT 인증, 역할 기반 라우트 가드 | 로그인·역할 구분·담당 환자 접근제어는 있음. 공식 기준의 "계정 관리" 세부 요건(예: 계정 잠금 정책, 비밀번호 정책 등)과의 일치 여부는 확인 필요 |
| 의무기록 수정이력 | 부분 대응 | `ClinicalReport.last_modified_at`/`last_modified_by_user_id`, `AuditLog`의 `UPDATE_REPORT` | **보고서(ClinicalReport) 수준의 수정 시각·수정자는 기록됨.** 다만 원본 임상 레코드(`Diagnosis`/`LabResult`/`Prescription` 등) 자체의 필드별 변경 이력(이전 값/이후 값 diff)은 추적하지 않음 — `created_at`/`updated_at` 타임스탬프만 있고 버전 관리는 없음 |
| 감사기록 | 부분 대응 | `AuditLog` 모델(`LOGIN`/`VIEW_REPORT`/`CREATE_REPORT`/`UPDATE_REPORT`/`APPROVE_REPORT`/`REJECT_REPORT`/`GENERATE_REPORT_NARRATIVE` 등 action 기록) | 주요 작업에 대한 감사 로그는 실제로 쌓이고 있음. 공식 기준이 요구하는 보관 기간, 위변조 방지, 로그 자체의 무결성 검증 등 세부 요건은 확인 필요 |
| 개인정보 보호 | 부분 대응 | JWT 기반 인증, 역할 기반 접근제어, 환자용 화이트리스트 스키마(`PatientClinicalReportDetail`), 합성 데이터만 사용 | 기본적인 접근제어·최소노출 설계 원칙은 적용되어 있음. 2024년 보도자료가 언급한 "개인정보 보호법 개정 반영 12개 기준"의 구체적 항목과 이 프로젝트의 설계가 일치하는지는 세부기준 원문 미확인으로 판단 불가 |
| 백업·복구 | 미구현 | Docker 볼륨(`db_data`)에 데이터가 남아 있을 뿐, 별도 백업 절차나 복구 정책은 없음 | 로컬 개발 환경 수준이며 공식 기준이 요구하는 백업·복구 체계는 설계된 바 없음 |
| 상호운용성 | 미구현 | 없음 | FHIR/KR Core 등 외부 표준 규격으로의 데이터 교환 기능이 전혀 없음. **근거 보강(2026-11-05): KR Core Implementation Guide v1.0.2(STU1, HINS/HL7 Korea 공식 게시)의 실제 존재와 Profile 구조(Patient/Encounter/Condition/Observation/MedicationRequest/AllergyIntolerance/Procedure/VitalSign 7종 등)를 공식 페이지에서 직접 확인했다** — 다만 이 프로젝트가 이 표준을 실제로 구현한 것은 아니며, `kr-cdi-kr-core-mapping.md`의 매핑표가 그 설계 1단계일 뿐이다 |

## 3. 요약

현재 프로젝트는 **임상 데이터 기록·관리의 기본 뼈대(환자정보/진단/검사/처방/알레르기/계정·권한/감사기록)에서 "부분 대응" 수준**이고, **활력징후·수술/처치·백업복구·상호운용성은 "미구현"**이다. 어떤 항목도 공식 기준과의 세부 일치 여부를 "충족"으로 단정하지 않았으며, 다수 항목이 세부기준 원문(emrcert.mohw.go.kr) 미열람으로 "확인 필요" 성격을 함께 가진다.
